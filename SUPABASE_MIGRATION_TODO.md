# Supabase Migration — Remaining Work

Tracks what's left in the Supabase backend migration (see `docs/adrs/002_supabase_backend_poc.md` and `docs/adrs/003_coppa_child_data_deletion.md` for the decisions behind this work). Update this as phases complete — delete it once the migration is fully done and its content has been folded into the ADRs / README.

## Status as of Phase 10

Phases 1–10 done: project scaffolding, real Supabase Auth, Field Guide as the CRUD+RLS vertical slice, the event-cancellation server-push pipeline (verified to the FCM credentials boundary), full Profile completion, Challenges, Events (full feature), Today dashboard composition, and now the Chapter dropdown off Supabase. All three of ADR 0002's POC success criteria are met at the backend level. 24 widget tests pass, `flutter analyze` clean. Only Phase 9 (remaining reminder types, blocked on Firebase) and the cross-cutting "derive real household labels on Guide" follow-up remain.

Phase 10 notes:
- New `ChapterRepository`/`StaticChapterRepository`/`SupabaseChapterRepository` (`lib/shared/data/chapter_repository.dart`) + `chaptersProvider` (`lib/shared/providers/chapter_providers.dart`), replacing all 5 direct `seedChapters` call sites (`sign_up_captain_screen.dart`, `sign_up_guardian_screen.dart`, `my_kids_screen.dart`, `edit_profile_screen.dart`, `child_form.dart` + its two parent screens). `seedChapters`/`Chapter` itself stays — it's now just `StaticChapterRepository`'s backing data for tests/Widgetbook.
- **Real constraint found while wiring this up, not anticipated by the plan**: the Captain/Guardian sign-up screens populate and let the user pick from the Chapter dropdown *before* `auth.signUp()` ever runs — there is no session yet at that point. The plan's original RLS design (`chapters` readable `to authenticated` only, same as the rest of reference_content) would have left that dropdown empty pre-auth. Fixed with a new migration (`chapters_anon_read`) widening just this one table's read policy to `anon, authenticated` — chapters are non-sensitive public directory data (name/city/meeting time), so this is safe; every other reference/user table stays `authenticated`-only exactly as designed.
- Verified directly against the real stack: `curl` with the anon key/no session reads `chapters` fine (33 real seeded chapters, e.g. "Christ the King", "Holy Ghost") but gets `42501 permission denied` on `members` — proving the widened policy is scoped to just the one table, not a blanket anon-read regression.
- **Also got a genuine interactive pass via Appium** (see UI automation note below): fresh-installed the app (to clear a stale pre-`db reset` auth session — see the note in that section), signed out, walked Sign Up → Guardian → "I also attend Fraternus meetings myself" → tapped the Chapter field, and confirmed the native picker wheel populated with real chapter names pulled live from Supabase pre-authentication ("St. Rose of Lima", "St. Philip", "St. Paul", "St. Patrick", ...) — not the old 3-entry `seedChapters` list. Selected one and confirmed it round-tripped back into the field correctly.
- **Environment gotcha worth keeping in mind**: `supabase db reset` regenerates all data (including auth users) with fresh ids, but the simulator app keeps its previously-persisted Supabase session (via `noReset: true`/normal app storage) pointing at a now-nonexistent user. This produced a confusing symptom — the tab shell rendered (client-side redirect logic saw a session) but all content stayed blank forever (the underlying `users`/`members` fetches errored on a foreign id with no visible error surfaced, since the loading branch and a silently-stuck-in-error branch can look identical at a glance). Fixed by `xcrun simctl uninstall <udid> <bundleId>` + a fresh `flutter run` to force a clean install with no persisted session. Worth remembering for any future phase's Appium pass right after a `db reset`.

Phase 8 notes (client composition only — no schema/RPC changes this phase):
- `TodayDashboardRepository`/`StaticTodayDashboardRepository` deleted. `todayDashboardProvider` (today_providers.dart) now composes `TodayDashboard` from `CurrentUser`, `HouseholdMembers`, `guideWeekForDateProvider`, `currentChallengeProvider`, `guideDevotionalProgressProvider`, `challengeProgressProvider`, and `visibleEventsProvider` — no dedicated aggregator RPC, per the plan's decision notes.
- A person's Today status (none/in-progress/done) is computed from the same two completion booleans `_TodayTaskCard` already used (field guide + current challenge) — nothing new invented, just reused where the person-tab badge used to be hardcoded seed data.
- Per-person event tasks are now filtered through `event.eligibleHouseholdMembers` — the old static seed showed the same events under every person's list regardless of role; real data makes that a real bug (e.g. a Brother seeing a Captains-only meeting) if left unfiltered, so it's filtered now.
- "Events later this week" uses a simple rolling 7-day-from-today window (excluding today's own events, which show under each person instead) — there's no other calendar-week concept anywhere else in this app to anchor "this week" to more precisely.
- Found and fixed a real crash risk surfaced by switching to real data: `today_screen.dart`'s `_TodayContent` did a bare `people.firstWhere(...)` with no `orElse`, and `TodaySelectedPerson`'s default key (`'you'`) will never match a real UUID Member id — previously masked by static seed data that always contained a `'you'` entry. Fixed with a null-safe empty-household state ("Add a household member from Profile to get started.") plus an `orElse` fallback to the first person, and `PersonTabs`' `activeKey` now follows the resolved person so the correct tab actually highlights (Challenge/Guide/Events still have the same `'you'`-default cosmetic quirk under the broader "derive real labels" item below — not touched here, out of scope for this phase).
- Verification: `flutter analyze`/`flutter test` clean (all 24 tests pass without any test-file changes — the existing Static* fakes wire straight through). **Also got a real end-to-end UI pass** (see "UI automation" note below) — signed in as a real Supabase account and confirmed the composed Today screen live: correct real date/greeting, real member name on the person tab (not `'you'`), "Captain Meeting" correctly appearing as a today-task (Greg is a Captain, the event is captains-only — the `eligibleHouseholdMembers` filter is doing real work), empty Guide/Challenge/"later this week" states all rendering their friendly fallbacks with no crash.

**UI automation note**: AppleScript/`osascript`-driven clicking and typing into the iOS Simulator (used for Phase 7's first verification attempt) turned out to be fundamentally unreliable in this environment — a real `screencapture` of the physical display showed a completely empty desktop with no visible windows at all, even though `xcrun simctl io screenshot` (which reads the simulator's framebuffer directly, not the screen) looked normal. There is no real interactive desktop session here for synthetic mouse/keyboard window-system events to land in. **Appium (with the XCUITest driver) fixes this** — it drives the simulator through XCTest's own IPC protocol, not macOS window/screen coordinates, so it works regardless of that limitation, and this is now how both Phase 7 and Phase 8 got a genuine interactive pass (see below). One local install snag: the `xcuitest` driver installed via `appium driver install` under `~/.appium/node_modules` couldn't resolve its `appium` peer import (Homebrew's `appium` binary lives in a separate Cellar path) — fixed with `cd ~/.appium && npm install appium@<matching version>`. Also worth knowing: Flutter's obscured password field shows up in the accessibility tree as `XCUIElementTypeSecureTextField`, not `XCUIElementTypeTextField` — querying only the latter will silently miss it. **Use Appium for interactive simulator verification going forward** instead of AppleScript. Basic recipe: `appium server -p 4723 &`, `POST /session` with `platformName: iOS`, `appium:automationName: XCUITest`, `appium:udid`, `appium:bundleId`, `appium:noReset: true`; then `POST /session/:id/element` (`using: "accessibility id"` or `"xpath"`) + `/click` + `/value`, and `GET /session/:id/screenshot` to verify.

**A real bug was only caught because of this real interactive pass**: tapping "Going" a second time on an event's RSVP row (the toggle-off/un-RSVP path) silently failed to update the UI — the row visually stayed highlighted even though the database correctly deleted it (confirmed by direct psql query). Root cause: `submit_event_rsvp`'s toggle-off path returns a Postgres composite row that's SQL `NULL` as `{"id": null, "event_id": null, ...}` over the wire — an object with all-null fields, not a bare JSON `null` (same gotcha `toggleChallengeRep` already had a comment about, but `SupabaseEventsRepository.submitRsvp` only checked `result == null`, not `row['id'] == null`). That let `HouseholdRsvp.fromJson` throw on `null as String`, which silently killed the `toggleStatus` notifier method before it reached `ref.invalidate(visibleEventsProvider)` — no crash, no error surfaced anywhere in the UI, just a screen that quietly stopped reflecting reality. Fixed to match `toggleChallengeRep`'s pattern; reverified through the same tap-twice sequence via Appium and confirmed the toggle-off now reflects immediately. **This class of bug — an unhandled exception inside a fire-and-forget `onChanged: () => notifier.method()` call — has no test coverage today** (widget tests don't exercise the real RPC's actual wire shape, and static analysis can't catch it); worth keeping in mind for Guide/Challenge's own toggle methods too, not just Events.

Phase 7 verification notes:
- Confirmed via curl+psql against the real stack: chapter-role eligibility (`chapter`/`captains`/`brothers`) resolves correctly per member role, `submit_event_rsvp` upserts, toggles off on re-selecting the same response, and updates in place on a different response; a stranger account gets `42501` trying to RSVP for a member they have no association with; PostgREST's nested embed returns the one-to-one detail tables (`event_frat_night_details`/`event_excursion_details`/`event_ranch_details`) as a single object (not an array) as expected, given the unique FK.
- Also got a real interactive pass via Appium (see UI automation note above): signed in as a real account, navigated Today → Events → event detail, tapped the RSVP toggle live, and caught the toggle-off UI bug described above.
- "Others Attending" — confirmed with the user this is a real business rule, not something to invent: any authenticated user can see who else has accepted ("Going") an event, even if they haven't RSVP'd themselves; their own household is excluded (shown separately via the RSVP section). Implemented as `get_event_attendees(event_id)`, a `security definer` RPC returning just `member_id`/`first_name`/`last_name` for accepted, non-own-household members — same "cross-household read gets its own narrow RPC" pattern as `get_event_eligible_members`, rather than widening `event_rsvps`'/`members`' RLS (which would've required loosening `members`' own read policy just to resolve names through a nested embed). Verified via curl with two separate households: a user who hasn't RSVP'd still sees the other household's accepted attendee; tentative/declined responses don't appear; a household never sees itself in its own list.
- Fixed an unrelated pre-existing bug blocking `db reset` entirely: `supabase/migrations/20260818180001_frat_night_templates_virtue_key.sql` (an in-progress migration switching `frat_night_templates` to reference `frat_night_virtues` by a natural `key` instead of `id`) used a correlated subquery inside `ALTER COLUMN ... TYPE ... USING`, which Postgres rejects (SQLSTATE 0A000). Rewrote as add-column/populate-via-join/drop/rename.

Earlier real-stack bugs (Phases 5–6, for reference — keep testing every phase's actual write/read path against a live instance, not just stub data):
- Phase 5: a client-direct `INSERT` on `user_reminders`/`user_devices` that omits `user_id` sends `NULL`, and `with check (user_id = auth.uid())` evaluates `NULL = uuid` as `NULL` (not true) — same generic RLS-violation error a real cross-user attempt gets. Fixed with `default auth.uid()` on both tables.
- Phase 6: `has_challenge_member_association()` was used in policies before it was ever defined anywhere. Had to add it to the `challenges` migration itself (not the earlier `members_and_associations` migration) since it references `challenge_members`, which doesn't exist until then.

## Blocking external setup (not something I can do autonomously)

1. **Firebase project** — needed to actually deliver push notifications (Phase 4's cancellation pipeline is built and tested up to this point; Phase 9's remaining 6 reminder types need it too). Steps once you have one:
   - Enable Cloud Messaging.
   - Create a service account with the Firebase Cloud Messaging API role, download its JSON key.
   - iOS: upload an APNs auth key (Firebase Console → Project Settings → Cloud Messaging → Apple app config) — without this, iOS can't receive pushes at all, regardless of app code.
   - `supabase secrets set FCM_SERVICE_ACCOUNT_JSON='<json, one line>'`, `FCM_PROJECT_ID`, and `WEBHOOK_SECRET` (must match the value passed to `vault.create_secret('<value>', 'webhook_secret')` — see the events migration).
   - Add `firebase_core`/`firebase_messaging` to the Flutter app, wire `Firebase.initializeApp()`, build a device-token repository that upserts into `user_devices`. Deliberately not started yet — adding the dependency without real config files (`GoogleService-Info.plist`/`google-services.json`) risks breaking the native build in ways that can't be verified without them.

2. **Hosted Supabase project** — everything so far is local-only (`supabase start`). Before this ships:
   - Create the hosted project, `supabase link --project-ref <ref>`, `supabase db push`.
   - Run the one-time `select vault.create_secret(...)` webhook-secret setup against the hosted DB too (separate from local's).
   - Fill in `fraternus_mobile_app/env/prod.json` from `env/prod.example.json` with the hosted project's URL/anon key.
   - Deploy Edge Functions: `supabase functions deploy notify-event-cancellation`.

## Cross-cutting follow-ups (not tied to one phase)

- ~~**Derive household member lists/labels from real `Member` records.**~~ — done. Guide was the last holdout (`guide_screen.dart`'s hardcoded `_personLabels` map + iterating the fetched devotional's own `members` for the tab list); Today/Challenge/Events already did this. Fixed with a new `guideHouseholdProvider` (mirrors `challengeHouseholdProvider` exactly: `householdMembersProvider` → `GuideHouseholdMember(memberId, label: member.firstName)`), and `guide_screen.dart` now builds `PersonTabs` from that list instead of `devotional.members`. **This wasn't just a labeling fix — it was a real, previously-undiscovered bug**: `field_guide_daily_devotional_members` rows are only created lazily (on first `upsertDevotionalMember` call for that member/day), so a household member who hasn't touched today's reading yet has *no row at all* — iterating `devotional.members` would have silently hidden their tab entirely, not just mislabeled it. Caught and confirmed via a genuine Appium pass: signed up a fresh Guardian ("Maria"), added a child ("Leo") who had never touched any devotional, seeded a real Field Guide week/devotional via SQL for today's date, and confirmed **both** tabs rendered on first load (pre-fix, Leo's would have been missing). Also verified the write path both ways: tapping Mark Complete as Maria (a Captain, so COPPA's `member_is_write_active` passes) correctly created her row and updated the streak/checkmark live; tapping it as Leo (a Brother under 13 with no granted guardian consent yet) correctly did nothing — RLS blocked the insert, which is the *correct* COPPA behavior, not a bug, and a good reminder that consent-granting (see below) is still a real gap. This drops the "You" special-casing the self Member used to get (Maria's own tab shows "Maria", not "You") — same already-accepted tradeoff Today/Challenge/Events made. `GuideSelectedPerson.build() => 'you'` was deliberately left as-is (same cosmetic-only "no tab starts active" quirk `TodaySelectedPerson`/`ChallengeSelectedPerson` already have, not a crash — Guide's `progressByPerson[selectedKey]` lookup just returns null on a miss).
- **Appium accessibility-id gotcha found this session**: `using: "accessibility id"` matches the widget's actual semantic *label* string, not its on-screen (often CSS-uppercased) rendered text — e.g. a `PersonTabItem` labeled `"Maria"` in code renders as "MARIA" on screen but only responds to a lookup for `"Maria"`; searching for `"MARIA"` silently returns no element. Same for the bottom nav ("Guide" not "GUIDE"). When an accessibility-id lookup unexpectedly 404s on visible text, try the un-uppercased label before falling back to coordinate taps.
- **Consent-granting verification flow.** Revocation is done (UI lives on Edit Child, tested against both the fake and — via the same RLS UPDATE policy exercised in Phase 4's pipeline test — the real stack). *Granting* consent plausibly needs a real verification mechanism (e.g. an emailed confirmation link hitting an Edge Function) — intentionally left undesigned, not just unbuilt. No UI or backend path exists for it yet.
- ~~`HouseholdAssociations.remove`~~ — done, removed; the whole class was simplified to a plain function provider since nothing mutates it directly anymore.
- **ADR 0002 §3 supersession note.** This work moved reference content (Chapters, Field Guide content, Frat Night templates, Events) into Postgres, which is broader than ADR 0002 §3's literal framing ("reference content stays bundled"). Worth a short note added to ADR 0002 itself acknowledging this, same pattern ADR 0002 used against ADR 0001 — not yet written.
